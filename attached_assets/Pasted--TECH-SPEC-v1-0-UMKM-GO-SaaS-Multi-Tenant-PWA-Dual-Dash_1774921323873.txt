- Public marketing pages
- Auth pages
- Tenant dashboard
- Admin dashboard
- Tenant storefront
- API endpoints
- Background jobs
- Webhooks

## 3.3 Architecture Pattern
- Frontend rendered via Next.js
- Data access via server actions / route handlers / backend endpoints
- Multi-tenant isolation via auth + tenant context + RLS + tenant-scoped repository pattern

- CMS-driven marketing content
- Feature gating driven by subscription entitlements

# 5. TENANT RESOLUTION STRATEGY

## 5.1 Tenant Context Sources
Tenant context dapat berasal dari:
- authenticated session pada dashboard tenant
- slug pada public storefront
- verified custom domain mapping
- admin impersonation context yang tervalidasi

## 5.2 Resolution Order for Public Storefront
1. Check host header
2. Jika host = custom domain tenant → resolve tenant by domain
3. Jika host = main platform domain → parse `/:storeSlug`
4. Load tenant context
5. Validate tenant storefront status
6. Render storefront

## 5.3 Resolution Order for Dashboard
1. Read authenticated session
2. Resolve owner / member -> tenant membership
3. Load active tenant context
4. Load entitlements
5. Enforce feature access

## 5.4 Technical Rule
Tenant ID **tidak boleh** diambil mentah dari query param atau client payload sebagai sumber kebenaran.  
Semua query data harus memakai tenant context hasil validasi server-side.

## 6.2 Admin Auth
- Separate admin login

- Optional device/session audit

## 6.3 Tenant Roles
- owner
- operator
- viewer

## 6.4 Admin Roles
- super_admin
- support
- finance
- content_admin

## 6.5 Authorization Strategy
Authorization dilakukan di 3 level:
1. UI gating
2. API route authorization
3. Database / repository tenant-scoped enforcement

## 6.6 Impersonation Rules
- Hanya role tertentu yang dapat impersonation
- Wajib mengisi reason

- Tombol exit impersonation wajib selalu terlihat

# 10. DATABASE ACCESS STRATEGY

## 10.1 Isolation Model
- Shared PostgreSQL database
- Shared tables with `tenant_id`
- RLS enabled on tenant-owned tables
- Optional app.current_tenant context for deeper enforcement
- Admin tables separated logically

## 10.2 Required Rules
- all tenant-owned records must have `tenant_id`
- no tenant query without tenant filter
- no direct update/delete without ownership validation
- no sequential public identifiers exposed where sensitive

## 10.3 Query Patterns
Safe pattern:
- `WHERE tenant_id = currentTenantId AND id = resourceId`

Unsafe pattern:
- `WHERE id = resourceId` only

## 10.4 Caching Rules
- all cache keys prefixed by tenant identifier
- cache payload can include tenant ID for validation
- cache invalidation must support tenant-scoped purge

# 17. PWA TECHNICAL DESIGN

## 17.1 PWA Goals
- installable app-like experience
- faster repeat visits
- dashboard shell loads fast
- offline fallback
- resilient mobile UX

## 17.2 Required Files
- `/manifest.webmanifest`
- service worker script
- app icons 192x192 and 512x512
- offline fallback page

## 17.3 Manifest Fields
- `name`
- `short_name`
- `start_url`
- `display: standalone`
- `theme_color`
- `background_color`
- `icons`

## 17.4 Service Worker Responsibilities
- precache essential shell assets
- cache static assets
- cache offline page
- use safe cache versioning
- handle fetch strategies by route type

## 17.5 Cache Strategy by Surface
- marketing assets: stale-while-revalidate
- storefront assets: stale-while-revalidate / cache-first for images
- dashboard shell: network-first with cached shell fallback
- admin shell: network-first, minimal cache
- offline page: precached

## 17.6 Offline UX
- custom offline page
- reconnect notice
- fallback for unavailable network actions
- keep shell usable where possible

# 26. ENGINEERING DECISIONS

## 26.1 Recommended Defaults
- shared DB + RLS for MVP
- one tenant per owner for MVP
- one active subscription per tenant
- one primary custom domain
- mobile-first for tenant
- desktop-first for admin

## 26.2 Intentional Simplifications
- no full offline transactional support in MVP
- no multi-warehouse
- no native mobile app
- no advanced automation engine
- no multi-tenant marketplace aggregator in MVP
